## Три представления симуляции

Результат сварочного расчёта нельзя показать одной картинкой: это функция и **места**, и **времени**.
Инженеру нужны три среза этих данных:

1. **Поле в момент времени** — сцена: где сейчас горячо (шаг 7).
2. **Поле на плоскости** — сечение: что внутри (шаг 8).
3. **Время в точке** — термический цикл: как точка нагревалась и остывала (этот шаг).

Ценность — в **связи** между ними: клик по детали даёт кривую, клик по кривой переводит сцену на
этот момент.

## 9.1 Единая точка смены шага

```ts
function goToStep(step, fromUser = true) {
  field.setStep(step);     // атрибут aScalar → GPU
  setStepSlider(step);     // ползунок (без вызова его onChange — иначе цикл)
  drawSection();           // 2D-сечение
  chart.setStep(step);     // вертикальная линия и точки на кривых
  showPickInfo();          // T в панели выбора
  if (fromUser && player.playing) player.restartFrom(step);
}
```

Шаг меняют трое: ползунок, график и проигрывание. Все идут **через одну функцию**. Если бы каждый
обновлял представления сам, рано или поздно кто-то забыл бы одно. Так было на шаге 7: T в панели
выбора не обновлялась при смене шага. Теперь это исправлено попутно, потому что `showPickInfo` —
одно из представлений шага.

Сеттеры панели (`setStepSlider`) выставляют значение **без** вызова `onChange` — так устроены все сеттеры панели с
шага 5. Иначе `goToStep → ползунок → onChange → goToStep → …`.

## 9.2 Проигрывание и рендер по требованию

```ts
playbackStep(startStep, elapsedMs, stepsPerSecond, count)
  = (startStep + floor(elapsedMs · rate / 1000)) % count
```

**Шаг — по прошедшему времени, а не «+1 за кадр».** Иначе скорость зависела бы от частоты экрана
(на 144 Гц в 2.4 раза быстрее, чем на 60) и от пропущенных кадров. Тест: старт 40 из 45, 10 шагов/с,
750 мс → 47 → по кругу → 2.

Встроено так же, как инерция орбиты (шаг 4): слушатель `onBeforeRender`, пока `playing`, снова
вызывает `requestRender()`, и цикл кадров крутится. На паузе запросов больше нет, и
`requestAnimationFrame` останавливается сам. Флаги и таймеры не нужны.

Замер: за 1 с при 8 шагах/с прошло ровно 8 шагов (25 → 33) и отрисовался 61 кадр. После паузы
дорисовался один уже запланированный кадр, дальше 0.

**Что можно лучше.** Во время проигрывания рисуется 60 кадров в секунду, хотя картинка меняется
8 раз. План это допускает («рендер идёт непрерывно — это нормально»). Экономнее перерисовывать
только при смене шага: ждать следующего шага через `setTimeout` до момента
`startTime + (k+1)·1000/rate` и только тогда `requestRender()`. Для ноутбука на батарее разница
заметна, и это хороший вопрос «что бы вы улучшили».

`restartFrom(step)`: пользователь сдвинул ползунок или кликнул по графику во время проигрывания —
отсчёт начинается заново от нового шага, а не прыгает обратно к расчётному.

## 9.3 Зонд

- **Клик** по детали — выбор (шаг 6) плюс зонд вместо всех прежних.
- **Shift + клик** — ещё один зонд, до четырёх (самый старый уходит). Цвет маркера в сцене = цвет
  кривой на графике.

Кривая — **та же барицентрия**, что у `valueAt` на шаге 7, только по всем шагам:

```ts
cycleAt(steps, [a, b, c], bary)  // → Float32Array: T_a·w_a + T_b·w_b + T_c·w_c на каждом шаге
```

В плане предлагалась **ближайшая вершина**. Интерполяция лучше: значение на графике совпадает с
цветом под маркером и с числом в панели выбора. С ближайшей вершиной они расходились бы на
крупной сетке.

Зонды сбрасываются при смене детали или единиц: они держат индексы вершин старой геометрии.

## 9.4 t8/5 — главное число термического цикла

**t8/5** — время остывания с 800 до 500 °C. В этом интервале аустенит превращается в феррит, перлит,
бейнит или мартенсит, и **скорость** прохождения интервала определяет, что получится в ЗТВ: быстро —
твёрдый хрупкий мартенсит (риск холодных трещин), медленно — мягкие структуры. Сварщик регулирует
t8/5 погонной энергией и подогревом.

```
coolingTime(curve, 800, 500):
  найти пик
  после пика: шаг, где кривая пересекает 800 сверху вниз (линейная интерполяция между шагами)
  после пика: то же для 500
  разность — или null, если не нагрелась до 800 или не успела остыть до 500
```

Ловушка, которую ловит тест: при **нагреве** кривая тоже проходит через 800 °C. Искать надо только
после пика. Тест: `[20, 1000, 900, 700, 600, 400, 300]` → 800 °C на шаге 2.5, 500 °C на 4.5 → 2.

Проверка на демо: зонд на шве — пик 1739 °C, **t8/5 = 2.5 шага**. По модели остывания избыток
умножается на 0.82 за шаг. Время от избытка 780 до 480 °C: ln(480/780) / ln(0.82) ≈ **2.45 шага** —
сходится (разница от линейной интерполяции между шагами).

Шаги у нас безразмерные. В настоящем расчёте у шага есть длительность, и t8/5 будет в секундах
(типично 5–30 с для конструкционной стали).

## 9.5 График

Обычный 2D-канвас, без библиотек (ADR 0001):

- ось T фиксированная 0–2000 °C — как фиксированный диапазон легенды (ADR 0007): кривые разных
  зондов и разных расчётов сравнимы;
- пороги 1500 / 900 / 720 °C пунктиром, как на легенде; полоса 800–500 °C — окно t8/5;
- вертикальная линия — текущий шаг, точки на кривых — значения в этот момент;
- справа: T сейчас, пик, t8/5 по каждому зонду.

**HiDPI:** размер буфера канваса = CSS-размер × `devicePixelRatio`, затем
`ctx.setTransform(dpr, …)`, и дальше рисуем в CSS-пикселях. Без этого на ретине линии и текст
размыты — та же история, что с `setPixelRatio` у рендерера на шаге 1.

**Клик и протяжка:** `stepAtX` — ближайший шаг, прижатый к краям. На `pointerdown` вызывается
`setPointerCapture`, чтобы протяжка продолжалась, даже если мышь ушла с канваса. `touch-action: none` —
чтобы на тач-экране протяжка не прокручивала страницу.

Скриншоты: `step9-probes.png` (три зонда поперёк шва: 1739 / 612 / 41 °C в пике),
`step9-linked.png` (шаг 25 выставлен протяжкой по графику; сцена, ползунок и T в панели — те же 25).

## Хранение данных по времени (ADR 0009)

Сейчас **все шаги в памяти**: 45 шагов × 17 038 вершин × 4 байта ≈ 3 МБ. Смена шага — копия в
буфер атрибута, график строится мгновенно (кривая — проход по всем шагам).

Для настоящего расчёта (миллион узлов × тысяча шагов × 4 байта = **4 ГБ** на одну величину) так
нельзя. Варианты:

- **Потоковая подгрузка шагов** по запросу (HTTP Range, чанки) с кешем ближайших — для анимации.
- **Хранение «по точкам»** (транспонированное) или отдельный запрос на сервер для термического
  цикла: кривая в одном узле по всем шагам — это чтение одного «столбца», а не всех шагов целиком.
- **Сжатие**: Float16, квантование в 8/16 бит относительно диапазона, разностное кодирование соседних
  шагов (поле меняется плавно).

Значит, у графика и у сцены разные шаблоны доступа к данным: «все узлы, один шаг» против «один
узел, все шаги». Это главный вопрос архитектуры данных для такого вьюера.

## Что уметь объяснить

- Три представления симуляции и зачем их связывать
- Почему смена шага — одна функция; как избежать цикла ползунок ↔ обработчик

- HiDPI-канвас, `setPointerCapture`, `touch-action`
