## Разбор кода `viewer.ts`

### Конструктор

```ts
this.renderer = new THREE.WebGLRenderer({ canvas, antialias: true });
```

Рендерер не создаёт свой `<canvas>`, а берёт наш из `index.html`. Так разметкой и размерами
управляет CSS (шаг 0), а не three. `antialias: true` включает MSAA: сглаживаются края
треугольников. Включить его можно **только при создании контекста WebGL**, потом поменять нельзя.

```ts
this.renderer.setPixelRatio(Math.min(window.devicePixelRatio, 2));
```

На экране с `devicePixelRatio = 3` канвас 1000×800 CSS-пикселей означал бы буфер 3000×2400 —
в 9 раз больше пикселей, чем при ratio 1. Работа фрагментного шейдера растёт пропорционально
числу пикселей, а глаз разницу между 2× и 3× почти не видит. Потолок 2 — стандартный компромисс.

```ts
this.camera = new THREE.PerspectiveCamera(45, 1, 1, 10_000);
```

**Временная камера**, просто чтобы было чем рисовать. `aspect = 1` — заглушка, настоящее значение
придёт из `resize()`. near/far = 1…10 000 мм: отношение 10⁴ пока безопасно. Как правильно
считать near/far от габарита, разберём на шаге 3.

```ts
new ResizeObserver(() => this.resize()).observe(canvas);
```

**Отличие от START.md:** там `window.addEventListener('resize', ...)`. Но размер канваса может
измениться и без изменения окна: сворачивается панель, меняется колонка grid. `ResizeObserver`
следит за самим элементом. Бонус: он срабатывает один раз сразу после `observe()`, поэтому
первый `resize()` (и первый кадр) случаются сами, без ручного вызова в конструкторе.

### Рендер по требованию

```ts
requestRender() {
  if (this.renderRequested) return;   // кадр уже запланирован — второй не нужен
  this.renderRequested = true;
  requestAnimationFrame(this.render);
}

private render = () => {
  this.renderRequested = false;
  this.renderer.render(this.scene, this.camera);
  ...
};
```

**Второе отличие от START.md**, и оно важное. В плане цикл крутится всегда и проверяет флаг:

```ts
// START.md — rAF вызывается 60 раз в секунду, даже когда рисовать нечего
private loop = () => {
  if (this.needsRender) { ...render... }
  requestAnimationFrame(this.loop);
};
```

У нас `requestAnimationFrame` планируется **только в момент запроса**. В покое браузер не будит
наш код вообще. Флаг `renderRequested` даёт **склейку**: если за один кадр пришло 10 изменений
(камера + палитра + данные), отрисовка будет одна. Это проверено: три `pointerdown` подряд
в одном тике дали +1 кадр.

Почему `render` — стрелочная функция-поле (`render = () => {}`), а не метод: её передают в
`requestAnimationFrame` как колбэк. Обычный метод потерял бы `this` при таком вызове.

Почему `renderRequested = false` стоит **до** `renderer.render`, а не после: если что-то внутри
отрисовки или в `onRender` снова вызовет `requestRender()` (так будет с инерцией на шаге 4),
запрос должен запланировать следующий кадр, а не потеряться.

### Ресайз

```ts
const { clientWidth: w, clientHeight: h } = this.canvas;
if (w === 0 || h === 0) return;
this.renderer.setSize(w, h, false);
this.camera.aspect = w / h;
this.camera.updateProjectionMatrix();
```

- `clientWidth/Height` — CSS-размер. `setSize(w, h, false)` выставляет буфер `w·ratio × h·ratio`
  и **не трогает** style (см. шаг 0).
- Проверка на 0: у скрытого канваса размер 0, а `aspect = 0/0 = NaN` испортит матрицу проекции.
- `updateProjectionMatrix()` обязателен: three не пересчитывает матрицу сам при смене `aspect`,
  `fov`, `near`, `far`. Забыть его — классическая ошибка «картинка растянулась при ресайзе».

### Подвох с `erasableSyntaxOnly`

Как и предупреждал шаг 0, `constructor(private canvas: ...)` не компилируется. Поле `canvas`
объявлено явно и присвоено в конструкторе.

## Про инерцию (подготовка к шагу 4)

У `OrbitControls` с `enableDamping = true` камера продолжает двигаться **после** того, как
отпустили мышь. Событий мыши больше нет, значит, никто не вызовет `requestRender()`, и камера
«замрёт» на полпути. Решение, которое сделаем на шаге 4: в отрисовке вызывать
`controls.update()`. Пока инерция не затухла, он генерирует событие `change` → `requestRender()`
→ следующий кадр. Затухла — событий нет, цикл останавливается сам. Именно поэтому важен
порядок `renderRequested = false` перед отрисовкой.

попал: его легко поменять одной строкой.

- В покое 2 секунды: счётчик кадров не изменился (1 → 1).
- Один клик → +1 кадр; три события в одном тике → +1 кадр (склейка работает).
- Изменение размера окна → кадр (ResizeObserver).

- `npm run build`: tsc без ошибок. Бандл вырос с 0.73 КБ до **525 КБ** (131 КБ gzip): это

  для одностраничного вьюера это нормально.
