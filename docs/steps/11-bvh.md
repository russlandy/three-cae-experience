## Результат — таблица

`node scripts/bench-pick.mjs` — 200 лучей, каждый попадает в деталь, одни и те же для всех вариантов:

| треугольников | перебор, мс | BVH, мс | ускорение | построение BVH, мс |
|---:|---:|---:|---:|---:|
| 32 384 | 0.683 | 0.005 | ×136 | 12 |
| 129 536 | 3.129 | 0.003 | ×1 059 | 32 |
| 518 144 | 12.472 | 0.002 | ×5 554 | 111 |
| 2 019 328 | 45.455 | 0.002 | ×26 762 | 417 |

Node v24, three r186, three-mesh-bvh 0.9.15. В браузере на 518 тыс. то же самое: **12.8 мс** перебором
против **3.5–8 мкс** с BVH, построение 102–107 мс.

Как читать:

- **Перебор растёт линейно**: ×62 треугольников → ×66 времени. На 2 млн это 45 мс на луч, то есть
  выбор при наведении мыши (hover) на 60 кадрах в секунду невозможен: бюджет кадра — 16 мс.
- **BVH почти не зависит от размера**: 2–5 мкс. Это O(log n): каждый уровень дерева отсекает
  большую часть треугольников. Рост в 64 раза — это 6 лишних уровней дерева.
- **Цена — построение**: ≈0.2 мкс на треугольник, линейно, и память на дерево. На 2 млн 417 мс
  окупаются примерно за 10 лучей. Для вьюера, где по одной детали кликают сотни раз, — однозначно
  да; для детали, которую покажут и сразу сменят, — можно строить лениво, по первому клику, или
  в Web Worker (у библиотеки есть `GenerateMeshBVHWorker`).

### Ошибка замера, которую я поймал

Первый прогон давал ×45 881 на 2 млн. В строке «попаданий» стояло **35/200**: лучи брались как
случайные точки экрана, и большинство летело мимо пластины. Для BVH промах почти бесплатный
(отсекается на корневой коробке), для перебора — нет: он всё равно проверяет все треугольники. То
есть замер **приукрашивал** BVH. Исправлено: лучи строятся через случайные точки верхней грани,
спроецированные на экран (`Vector3.project`), и попадают все 200. Ускорение на 2 млн честное —
×26 762.

Мораль для собеседования: в таблице замера должна быть колонка, которая доказывает, что сравниваются
одинаковые вещи.

## Решения

### Локально, без патча прототипов

README библиотеки предлагает:

```js
THREE.BufferGeometry.prototype.computeBoundsTree = computeBoundsTree;
THREE.Mesh.prototype.raycast = acceleratedRaycast;
```

Это меняет `raycast` **у всех** мешей приложения, включая маркеры, оси и чужой код. Я подключаю на
меши детали:

```ts
mesh.geometry.boundsTree = new MeshBVH(mesh.geometry, { indirect: true });
mesh.raycast = acceleratedRaycast;           // своё поле экземпляра закрывает метод прототипа
// выключить: raycast = THREE.Mesh.prototype.raycast, boundsTree = undefined
```

Так BVH можно выключить галочкой и сравнить на живой детали.

### `indirect: true` — не трогать индексный буфер

По умолчанию `MeshBVH` **переставляет треугольники в индексном буфере**, чтобы соседние по дереву
лежали в памяти подряд. Проверено: тот же луч без `indirect` дал треугольник №2854 вместо №2539. Для
нас это не критично (поле и подсветка идут по вершинам, а не по номеру треугольника), но номер
треугольника — данные, которые инженер может сверять с решателем. `indirect: true` хранит свой
порядок в дереве и оставляет геометрию как есть, ценой небольшой доли скорости.

Тест «результат с BVH = без BVH» сравнивает точку, нормаль и **набор** вершин треугольника, а не
номер — то, что важно для поведения.

### `firstHitOnly` и срез — ловушка, найденная тестом

`raycaster.firstHitOnly = true` (флаг библиотеки) — дерево останавливается на ближайшем
треугольнике. Но picking со срезом (шаг 8) **отбрасывает** попадания в отрезанную часть и берёт
следующее. С `firstHitOnly` следующего нет: ближайшее — отрезанное, его отбросили, результат `null`.
Тест «BVH + срез» упал ровно так (`Cannot read properties of null`). Решение:

```ts
raycaster.firstHitOnly = !clip;
```

Лучше — передать плоскость внутрь обхода дерева (`bvh.shapecast` с отсечением узлов по плоскости), но
для одного клика и тонкой детали разница — микросекунды.

### Замер в приложении: бюджет по времени

`measurePickMs` гонял луч 200 раз — без BVH на 0.5 млн это 200 × 12.8 мс ≈ **2.5 с** замороженного
интерфейса после клика. Теперь серия ограничена ещё и 50 мс: быстрому лучу — 200 повторов (нужны
из-за огрубления таймера), медленному хватит нескольких. Клик без BVH теперь отвечает за ~76 мс.

- **Бандл**: 675 → 743 КБ (+68 КБ, +21 КБ gzip).
- **ADR 0001** («только three») дополнен: `three-mesh-bvh` — сознательное исключение, задача которого
  измерима (таблица выше), а замена — свой BVH — это сотни строк и неделя отладки.
