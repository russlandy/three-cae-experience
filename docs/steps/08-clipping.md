## 8.1 Плоскость

Соглашение three: `d(p) = n·p + constant`. **`d ≥ 0` — остаётся, `d < 0` — отрезано.**

```ts
planeAt(box, 'x', 0.25)  // x₀ = lerp(min.x, max.x, 0.25) = −100 для пластины
// n = (−1, 0, 0), constant = x₀  →  d = −x + x₀ ≥ 0  ⇔  x ≤ x₀
```

Нормаль смотрит в **оставшуюся** часть, и отрезается сторона с большей координатой. Камера в
изометрии стоит в (+, +, +), поэтому отрезана ближняя к ней часть и срез сразу виден.

Объект `clipPlane` в main.ts один на всё время. `planeAt` меняет его **на месте**. Обычный материал
держит ссылку на него в `clippingPlanes`, и three каждый кадр читает актуальное значение. Шейдеру
поля uniform-вектор переписываем явно в `setClip`.

## 8.2 Отсечение в шейдере (ADR 0008)

```glsl
// вершинный
vec4 world = modelMatrix * vec4(position, 1.0);
vWorldPos = world.xyz;                       // → во фрагментный, интерполируется
// фрагментный, В САМОМ КОНЦЕ
if (uClipEnabled && dot(uClipPlane.xyz, vWorldPos) + uClipPlane.w < 0.0) discard;
```

`discard` — фрагмент не пишется ни в цвет, ни в глубину, будто треугольника там нет. Плоскость
задана в мире, поэтому нужна мировая позиция, а не позиция в пространстве камеры.

**Почему `discard` в конце, а не в начале.** Выше считается `fwidth(s)` для изотерм. Производные
GPU берёт, сравнивая соседние фрагменты в квадрате 2×2. Если часть квадрата ушла в `discard` до
этого, производные внутри ветвления формально не определены. В конце шейдера это уже неважно.

**Почему не встроенный `clippingPlanes`.** Для `ShaderMaterial` пришлось бы вставлять служебные
куски three (`#include <clipping_planes_pars_fragment>` и др.) и ставить `clipping: true`. Это
связь с внутренностями библиотеки ради одной строки. Зато для **обычного** материала детали (поле
выключено) встроенный путь правильный: `material.clippingPlanes = [plane]` плюс
`renderer.localClippingEnabled = true`, иначе three их молча игнорирует.

## 8.3 Полый срез — проблема, которую надо увидеть

Скриншот `step8-clip-y.png`: срез по Y на середине толщины. Сетка детали — только **поверхность**.
Внутри тела нет ни треугольников, ни значений. Отрезали верх, и внутри пустая коробка.

Что видно сквозь дыру:

- **без `DoubleSide`** — ничего: внутренняя сторона нижней грани смотрит от камеры, и её отбрасывает
  отсечение задних граней (back-face culling). Деталь выглядит как дырявый лист;
- **с `DoubleSide`** — изнанка дальних граней. Это быстрое решение из плана.

Но **чем красить изнанку?** Если полем, то это температура на поверхности дальней стенки (у Y-среза —
нижней грани), а глаз прочтёт её как цвет сечения. Ложная информация. Поэтому изнанка серая:

```glsl
if (!gl_FrontFacing) color = vec3(0.32) * (0.6 + 0.4 * lambert);
```

`gl_FrontFacing` GPU знает по обходу вершин треугольника на экране (против часовой — лицевая).

### Как делается по-настоящему: заглушка через трафарет (stencil)

Трафарет — 8-битный буфер на каждый пиксель, рядом с буфером глубины. В него можно писать и по
нему отсекать отрисовку.

1. Деталь с отсечением рисуется только в трафарет (цвет и глубина выключены): **тыльные** грани
   `+1`, **лицевые** `−1` (или одна операция «инвертировать» для обеих).
2. Луч из пикселя, который проходит через разрезанное тело, встречает «лишнюю» тыльную грань
   (передняя половина тела отрезана). В таких пикселях трафарет ≠ 0, в остальных 0.
3. Рисуем большой квадрат **в плоскости среза** с условием «трафарет ≠ 0». Получается заглушка
   ровно по форме сечения.
4. Обычный проход детали.

Цена: три прохода, порядок отрисовки (`renderOrder`), сетка обязана быть **замкнутой** — у дырявого
STL заглушка протекает. И главное: **покрасить** заглушку полем нельзя — внутри тела у нас нет
значений. В настоящем CAE они пришли бы из **объёмной** сетки (тетраэдры, гексаэдры), и на заглушке
интерполировали бы поле по ячейкам, которые режет плоскость.

Фраза для собеседования: «Срез у меня без заглушки — она делается трафаретным проходом, вот как.
Но заглушку надо ещё раскрасить, а для этого нужно поле внутри тела. Поэтому сечение я показываю
отдельно в 2D, где значения внутри есть».

## 8.4 Picking со срезом

Raycaster ничего не знает о плоскости среза — он пересекает треугольники. Без фильтра клик в
открывшуюся внутренность попадал бы в **невидимую** отрезанную грань впереди.

```ts
const hit = clip ? hits.find((h) => clip.distanceToPoint(h.point) >= 0) : hits[0];
```

`intersectObjects` возвращает попадания, отсортированные по расстоянию; берём первое с видимой
стороны. Изнанку Raycaster видит, потому что учитывает `material.side`, а при срезе он `DoubleSide`.
Проверено в браузере: срез по Y, клик в серое → точка `y = 0`, нормаль `(0, −1, 0)` — внутренняя
сторона нижней грани, а не отрезанный верх.

Найдено при проверке: маркер старого выбора оставался висеть в отрезанной части. Исправлено:
`updateClip()` сбрасывает выбор.

## 8.5 2D-сечение

Конвейер `sectionOf(геометрии, плоскость, ось, ячейка_мм)`:

```
sliceMesh        сетка ∩ плоскость → отрезки контура (3D)
  ↓ проекция на оси картинки u, v (sectionAxes)
sectionRaster    заливка строками: какие ячейки внутри
  ↓ центры ячеек обратно в мир:  p = −c·n + u·U + v·V
field.sample     поле той же модели в этих точках, по всем шагам
  ↓
SectionView      ячейка = пиксель, палитра, линии порогов
```

### `sliceMesh`: точка на ребре и вершины на плоскости

В треугольнике ищем рёбра, концы которых по разные стороны: `s = d_a / (d_a − d_b)`, точка
`a + s·(b − a)`. Смена знака бывает на двух рёбрах из трёх или ни на одном, поэтому получается
ровно один отрезок.

**Ловушка — вершина ровно на плоскости (`d = 0`).** У демо-пластины шаг сетки 2.5 мм, и срез на 50 %
(x = 0) проходит **ровно по ряду вершин**. Наивная проверка `d_a · d_b < 0` (строго разные знаки)
не видит ни одного пересечения, и сечение пропадает целиком. Тест «коробка 2×1×1 из двух
сегментов по X, срез по x = 0» это ловит (проверил мутацией: подставил наивную проверку — тест
упал с 0 вместо 4). Правило: `d = 0` **всегда** относится к одной стороне (у нас к «остаётся»). Тогда
каждое ребро считается ровно одним из соседних треугольников.

Честная оговорка по TDD: правило `d ≥ 0` я написал в первой же реализации, поэтому тест на ряд
вершин сразу был зелёным. Что он что-то ловит, показала мутация. Заодно выяснилось, что `d > 0`
(ноль на другую сторону) тоже правильно: важна последовательность, а не сторона.

### `sectionAxes`: картинка не должна быть зеркальной

Смотрим на сечение со стороны отрезанной части, как камера стандартного вида:

| Ось среза | u (вправо) | v (вверх) | как вид |
|---|---|---|---|
| X | −Z | +Y | «Сбоку» |
| Y | +X | −Z | «Сверху» |
| Z | +X | +Y | «Спереди» |

Тест — свойство, а не константы: `u × v` смотрит на зрителя (+ось). Если перепутать знак у одной
оси, картинка станет зеркальной: левый край шва окажется справа.

### `sectionRaster`: заливка строками по правилу чётности

Классика 2D-растеризации. Через центр каждой строки проводим горизонталь, находим её пересечения с
отрезками контура, сортируем. Внутри — между 1-м и 2-м, 3-м и 4-м пересечением… Отверстия
получаются сами: их контур добавляет ещё пару пересечений. Тест — квадрат 4×4 с отверстием 2×2.

Полуоткрытое правило `(v1 > v) !== (v2 > v)`: общая вершина двух соседних отрезков считается один
раз, горизонтальные отрезки не считаются вовсе. Порядок и направление отрезков не важны — контур
из `sliceMesh` неупорядоченный, собирать его в петли не нужно.

Размер ячейки подобран так, чтобы сечение влезло в 320 × 160 px, одна ячейка на пиксель и **без
растяжения**: мм по горизонтали и вертикали равны, форма ванны не искажена.

### Значения внутри тела

`FieldView.sample(points)` прогоняет ту же модель `generateField` по точкам ячеек. Это возможно,
потому что поле у нас синтетическое — функция координаты. **С настоящими данными так нельзя:**
решатель отдаёт значения в узлах сетки. Для сечения нужна объёмная сетка: плоскость режет
тетраэдры, значения интерполируются по их узлам (по тем же барицентрическим весам, только с
четырьмя вершинами). У поверхностной сетки (STL) внутри данных нет вообще.

### Линии порогов — как на макрошлифе

Пиксель белый, если сосед справа или снизу по другую сторону порога (1500 / 900 / 720 °C).
Скриншот `step8-clip-x.png` (шаг 14, срез поперёк шва): видна полукруглая ванна под источником и
вложенные границы Ac3 и Ac1 — по ним инженер судит о глубине проплавления и ширине ЗТВ. Настоящий
аналог — макрошлиф: образец разрезают поперёк шва и травят, и ЗТВ видна по структуре металла.
(Строго говоря, ЗТВ определяет **пиковая** температура за всё время, а не текущий шаг. Карта
максимума по шагам — естественное продолжение.)

## Что уметь объяснить

- Соглашение плоскости `n·p + c`, какая сторона остаётся; зачем мировая позиция в шейдере
- `discard`: что делает и почему в конце шейдера (производные, `fwidth`)
- Почему свой `discard` для поля и встроенный `clippingPlanes` для обычного материала;
  `localClippingEnabled`
- Почему срез полый (поверхностная сетка) и почему изнанка серая, а не цветная
- Трафаретная заглушка по шагам; почему ей нужна замкнутая сетка; почему её не покрасить полем
- Почему picking надо фильтровать плоскостью
- Разрез сетки плоскостью; вершина ровно на плоскости
- Заливка строками по правилу чётности, отверстия
- Поверхностная против объёмной сетки: откуда в настоящем CAE значения внутри тела
- Поперечное сечение шва: ванна, ЗТВ, связь с макрошлифом
