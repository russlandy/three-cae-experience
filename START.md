## Правила работы

1. **Один шаг — один коммит.** Название коммита = название шага. Потом по истории можно
   показать, как проект собирался.
2. **Числа важнее кода.** Везде, где можно замерить (треугольники, вызовы отрисовки, время
   кадра, время picking), — выводи на экран, а не в консоль.
3. **Никаких лишних библиотек.** Только `three`. Никакого React, никакого R3F, никакого UI-кита.
   Панель управления — обычный HTML справа. Причина: на собесе надо объяснять свой код, а не
   абстракции чужой библиотеки.
4. **Единица мира — миллиметр.** Как в рабочем проекте. Все внешние данные конвертируются
   ровно в одном месте — в загрузчике.
5. **Если застрял больше 40 минут** — переходи к следующему шагу, помечай в этом файле
   `[отложено]`. Полнота важнее, чем идеальность каждого пункта.

## Шаг 1. Рендерер, сцена и рендер по требованию

Это самый важный архитектурный шаг. Сделай его правильно сразу — потом переделывать больно.

### Что делаем

```ts
// core/viewer.ts
import * as THREE from 'three';

export class Viewer {
  readonly renderer: THREE.WebGLRenderer;
  readonly scene = new THREE.Scene();
  camera: THREE.Camera;
  private needsRender = true;

  constructor(private canvas: HTMLCanvasElement) {
    this.renderer = new THREE.WebGLRenderer({ canvas, antialias: true });
    this.renderer.setPixelRatio(Math.min(window.devicePixelRatio, 2));
    this.scene.background = new THREE.Color(0x1a1d21);
    // ...камера появится на шаге 3
    this.resize();
    window.addEventListener('resize', () => this.resize());
    this.loop();
  }

  /** Главный вход: что-то изменилось — надо перерисовать */
  requestRender() { this.needsRender = true; }

  private loop = () => {
    if (this.needsRender) {
      this.renderer.render(this.scene, this.camera);
      this.needsRender = false;
      // здесь обновляем панель счётчиков
    }
    requestAnimationFrame(this.loop);
  };

  private resize() {
    const { clientWidth: w, clientHeight: h } = this.canvas;
    this.renderer.setSize(w, h, false);
    // пересчёт камеры — шаг 3
    this.requestRender();
  }
}
```

### Почему рендер по требованию

Инженерный вьюер статичен большую часть времени: пользователь смотрит на модель и не трогает
мышь. Непрерывный цикл кадров жжёт батарею и мешает держать тяжёлые сцены. Рисуем только когда
что-то изменилось: подвинули камеру, сменили палитру, пришли новые данные.

Побочный эффект, про который надо знать: **инерция у орбиты (damping) требует непрерывного
цикла**, потому что камера продолжает двигаться сама. Либо отключаем инерцию, либо на время
затухания включаем постоянный рендер. Сделай второе — и расскажи про это на собесе, это
хороший признак внимательности.

### Проверка

Добавь временный куб `new THREE.Mesh(new THREE.BoxGeometry(100,100,100), new THREE.MeshNormalMaterial())`
и убедись, что он виден. `MeshNormalMaterial` не требует света — удобно на старте.

### Что уметь объяснить

- Зачем `setSize(w, h, false)` и чем внутреннее разрешение отличается от CSS-размера
- Почему `setPixelRatio` ограничен двойкой (на retina рисовать в 3× — впустую греть GPU)
- Что такое рендер по требованию, что он даёт и какой у него подвох с инерцией

## Шаг 2. Мир в миллиметрах: сетка, оси, масштаб

Сначала система координат, потом всё остальное. Если пропустить — потом не поймёшь, почему

### Что делаем

- `THREE.GridHelper(размер, деления)` — сетка-пол в плоскости XZ. Размер в миллиметрах:
  например 2000 мм с делением 100 мм.
- `THREE.AxesHelper` — оси. Подпиши их: X красная, Y зелёная, Z синяя (так по умолчанию).
- **Договорись о соглашении осей и запиши его в коде комментарием.** Three.js по умолчанию
  Y вверх. В CAD часто Z вверх. Выбери одно и придерживайся: предлагаю Y вверх (родное для

- **Масштабная линейка**: HTML-элемент внизу слева, который показывает, сколько миллиметров

Расчёт линейки для ортографической камеры простой: ширина области обзора в мире делится на
ширину вьюпорта в пикселях. Для перспективной — зависит от расстояния до точки интереса,

## Шаг 3. Две камеры, стандартные виды, fit-to-object

### Ортографическая камера

```ts
// высоту области обзора держим как состояние, ширину считаем из aspect
function makeOrtho(frustumHeight: number, aspect: number) {
  const h = frustumHeight / 2, w = h * aspect;
  return new THREE.OrthographicCamera(-w, w, h, -h, 0.1, 100_000);
}
```

При ресайзе **пересчитывай границы**, иначе картинка растянется. Зум у орто-камеры — это
изменение `frustumHeight`, а не приближение камеры.

### Перспективная камера

`new THREE.PerspectiveCamera(45, aspect, near, far)`. При ресайзе — `aspect` плюс
`updateProjectionMatrix()`.

**Про near/far.** Не ставь `near = 0.001` при `far = 100000`. Точность буфера глубины зависит
от **отношения** far к near, и при большом отношении дальняя часть сцены начнёт мерцать
(z-fighting). Считай near от габаритов модели: например `near = габарит / 1000`,
`far = габарит * 10`.

### Переключение орто ↔ перспектива

Главное: **сохранить то, на что смотрит пользователь**. При переключении переносим позицию,
направление взгляда и точку интереса; для орто подбираем `frustumHeight` так, чтобы объект
занимал примерно ту же часть экрана. Это нетривиально и на собесе это заметят.

Для перспективы: видимая высота на расстоянии `d` равна `2 * d * tan(fov/2)`. Отсюда при
переходе в орто бери `frustumHeight = 2 * d * tan(fov/2)` — и картинка почти не прыгнет.

### Стандартные виды

Клавиши: `1` сверху, `2` спереди, `3` сбоку, `0` изометрия. Вид — это позиция камеры на
заданном направлении от центра модели плюс `up`-вектор. Для вида сверху `up` нельзя оставить
равным Y (камера смотрит вдоль Y — вырождение), ставь Z.

### Fit to object

После загрузки модели камера должна сама встать так, чтобы объект был целиком виден:

1. `geometry.computeBoundingBox()`, взять центр и габарит (`box.getSize`).
2. Для орто: `frustumHeight = макс. габарит * 1.2`.
3. Для перспективы: `d = (габарит / 2) / tan(fov / 2) * 1.2`.
4. Поставить точку интереса в центр box, камеру — на расстоянии `d` по текущему направлению.

### Что уметь объяснить

- Почему для CAE орто по умолчанию (по ней можно мерить, параллельные остаются параллельными)
- Как зум устроен у орто-камеры и чем отличается от перспективной
- Откуда берётся z-fighting и как лечится
- Формулу `2 * d * tan(fov/2)` — она же нужна и для fit, и для переключения камер

## Шаг 4. Орбита, панорамирование и зум к курсору

### Вариант А — быстрый

`OrbitControls` из `three/addons/controls/OrbitControls.js`, у него есть
`controls.zoomToCursor = true`. Подключи `controls.addEventListener('change', () => viewer.requestRender())`.

### Вариант Б — обязательный

**Напиши зум к курсору сам, хотя бы для ортографической камеры.** Это ровно та задача,
которую ты уже решал в 2D-редакторе, и именно о ней будет интересно говорить.

Инвариант: **мировая точка под курсором остаётся под курсором после зума.**

Для орто-камеры алгоритм:

1. Перевести позицию мыши в NDC: `x = (px / w) * 2 - 1`, `y = -(py / h) * 2 + 1`.
2. Найти мировую точку под курсором до зума: построить луч через курсор и пересечь его с
   опорной плоскостью (сетка-пол) либо с геометрией. `raycaster.setFromCamera(ndc, camera)`,
   затем `ray.intersectPlane(plane, target)`.
3. Изменить `frustumHeight` на коэффициент зума, обновить проекционную матрицу.
4. Найти, куда теперь проецируется та же мировая точка, и **сдвинуть камеру на разницу**,
   чтобы вернуть точку под курсор.

Это та же конструкция «перенести — преобразовать — перенести обратно», что и в матрице
`T(p) * S * T(-p)`, только выраженная через сдвиг камеры.

Для перспективной камеры проще: двигай камеру **вдоль луча через курсор** к найденной точке,
а не вдоль направления взгляда.

Сделай сравнение: тумблер «зум к центру / зум к курсору». Разница ощущается сразу, и это
хорошая демонстрация понимания.

### Что уметь объяснить

- Формулу перевода пикселей в NDC и почему Y меняет знак
- Почему точка экрана в 3D — это луч, а не точка
- Как сохраняется инвариант зума и почему он важен для работы с чертежом

### Что заметить и записать в блокнот

- STL приходит **неиндексированным**: по три вершины на треугольник, вершины дублируются.
  Поэтому модель выглядит фасетированной — у каждой грани своя нормаль. Это не баг.
- glTF приходит как граф сцены (`gltf.scene`), в нём может быть много мешей, и по соглашению
  единицы — **метры**. То есть для glTF коэффициент по умолчанию 1000, для STL — спрашиваем.
- Если хочешь сгладить STL — `mergeVertices` из `three/addons/utils/BufferGeometryUtils.js`,

## Шаг 7. Скалярное поле температур — ядро демо

**Это самый важный шаг.** Здесь демо перестаёт быть «кубик крутится» и становится разговором
про их продукт.

### 7.1 Сгенерировать поле

Физику не считаем — имитируем движущийся источник тепла по линии шва.

```ts
// data/field.ts
// Шов — отрезок в мировых координатах. Источник идёт по нему за N шагов.
// Температура в точке: пик от гауссова источника + остаточное тепло от предыдущих шагов.

function temperatureAt(p: Vector3, sourcePos: Vector3, t: number): number {
  const d = p.distanceTo(sourcePos);
  const sigma = 18;                      // мм, размер зоны нагрева
  const peak = 1800;                     // °C в центре пятна
  const ambient = 20;
  const hot = peak * Math.exp(-(d * d) / (2 * sigma * sigma));
  // остаточное тепло: экспоненциальное остывание от того, что было нагрето ранее
  return ambient + hot;                  // на первом проходе достаточно
}
```

Дальше усложни: храни для каждой вершины текущую температуру и на каждом шаге делай
`T = ambient + (T - ambient) * cooling + hot`, где `cooling` около 0.82. Тогда за источником
останется остывающий след — и **график в точке даст настоящую форму термического цикла**:
быстрый подъём, пик, медленный спад. Это именно та кривая, по которой сварщик судит о
структуре металла, и она должна выглядеть правдоподобно.

Результат: массив `Float32Array` на каждый шаг времени, длиной в число вершин.
Для 20 шагов и 50 тысяч вершин это 4 МБ — спокойно держится в памяти.

### 7.3 Палитра как одномерная текстура

```ts
// data/palette.ts
const VIRIDIS = ['#440154','#482878','#3e4989','#31688e','#26828e',
                 '#1f9e89','#35b779','#6ece58','#b5de2b','#fde725'];

function paletteTexture(stops: string[], size = 256): THREE.DataTexture {
  const data = new Uint8Array(size * 4);
  // линейная интерполяция между стопами, заполнение RGBA
  const tex = new THREE.DataTexture(data, size, 1, THREE.RGBAFormat);
  tex.minFilter = tex.magFilter = THREE.LinearFilter;
  tex.wrapS = tex.wrapT = THREE.ClampToEdgeWrapping;
  tex.needsUpdate = true;
  return tex;
}
```

Сделай минимум две палитры: **viridis** и **радужную** (jet). Переключатель между ними — и
это твоя демонстрация того, почему радужная плохая: на одном и том же поле она покажет
ложные резкие границы там, где переход плавный.

### 7.4 Шейдер

`shaders/field.vert.glsl`:

```glsl
attribute float aScalar;
varying float vScalar;
varying vec3 vWorldPos;
varying vec3 vNormal;

void main() {
  vScalar = aScalar;
  vec4 wp = modelMatrix * vec4(position, 1.0);
  vWorldPos = wp.xyz;
  vNormal = normalize(mat3(modelMatrix) * normal);
  gl_Position = projectionMatrix * viewMatrix * wp;
}
```

`shaders/field.frag.glsl`:

```glsl
uniform sampler2D uPalette;
uniform float uMin;
uniform float uMax;
uniform float uIsoStep;        // 0 = изолинии выключены
uniform vec3  uClipNormal;
uniform float uClipConstant;
uniform float uClipEnabled;
uniform float uShade;          // 0..1 — доля подмешиваемого затенения

varying float vScalar;
varying vec3  vWorldPos;
varying vec3  vNormal;

void main() {
  // --- плоскость отсечения, вручную (см. примечание ниже) ---
  if (uClipEnabled > 0.5 && dot(vWorldPos, uClipNormal) + uClipConstant > 0.0) discard;

  // --- нормировка значения и выборка цвета ---
  float t = clamp((vScalar - uMin) / max(uMax - uMin, 1e-6), 0.0, 1.0);
  vec3 color = texture2D(uPalette, vec2(t, 0.5)).rgb;

  // --- изолинии: полосы по дробной части ---
  if (uIsoStep > 0.0) {
    float f = fract(t / uIsoStep);
    float w = 0.03;
    if (f < w || f > 1.0 - w) color *= 0.55;
  }

  // --- лёгкое затенение, чтобы читалась форма, но не врал цвет ---
  float lambert = max(dot(normalize(vNormal), normalize(vec3(0.4, 1.0, 0.6))), 0.0);
  color *= mix(1.0, 0.45 + 0.55 * lambert, uShade);

  gl_FragColor = vec4(color, 1.0);
}
```

**Два важных решения, которые надо уметь защитить:**

1. **Отсечение делаю вручную через `discard`, а не через `material.clippingPlanes`.** Причина:
   встроенный механизм Three.js требует в `ShaderMaterial` подключать его служебные вставки
   (`clipping_planes_pars_fragment` и соседние) и выставлять `clipping: true` — лишняя
   связанность с внутренностями библиотеки ради того, что в своём шейдере пишется одной
   строкой. Для материалов самой Three.js встроенный путь, конечно, правильный.
2. **Затенение по умолчанию почти выключено** (`uShade` около 0.25). Это не лень: в научной
   визуализации освещение искажает считывание цвета — один и тот же цвет на освещённой и
   затенённой стороне выглядит как разные значения. Поэтому поле показывают почти плоским, а
   форму читают по силуэту и изолиниям. Сделай ползунок `uShade` и покажи разницу — **это
   сильный аргумент, его почти никто не приводит**.

### 7.5 Легенда с физическими порогами

HTML-блок: вертикальный градиент из той же палитры, подписи минимума и максимума, и —
главное — **фиксированные отметки**:

- **1500 °C — температура плавления стали** → граница зоны сплавления
- **~900 °C и ~720 °C** — характерные температуры фазовых превращений → границы ЗТВ

Плюс тумблер **«диапазон: авто (min–max) / фиксированный»**. И объясни, почему авто в этой
задаче вредно: при автоматическом растяжении цвет перестаёт значить одно и то же между
шагами времени и между расчётами, и сравнивать картинки нельзя.

### Что уметь объяснить

- Почему скаляр подаётся атрибутом, а цвет берётся из текстуры, а не считается на CPU
- Как интерполируется значение между вершинами (varying → барицентрические координаты) и
  почему нельзя интерполировать цвет вместо значения
- Чем плоха радужная палитра (перцептивная неоднородность, ложные границы)
- Почему пороги легенды должны быть привязаны к физике, а не к min–max
- Почему освещение мешает читать поле

## Шаг 8. Срез: плоскость отсечения

- Ползунок двигает плоскость вдоль выбранной оси (X / Y / Z на выбор).
- Нормаль и константа идут в шейдер как uniform-переменные (уже есть в шаге 7).
- **Проблема, которую надо увидеть своими глазами:** отсечённое тело становится полым, видно
  изнутри и выглядит это неправильно. Два пути:
  - быстрый: рисовать меш с `side: THREE.DoubleSide` — внутренняя поверхность хотя бы
    закроет дыру, но срез будет не плоским;
  - правильный: трафаретный (stencil) проход — отрисовать «заглушку» плоскостью среза там,
    где она внутри тела.

Сделай быстрый, а про правильный расскажи словами. Признание «я знаю, что мой срез не
закрыт заглушкой, вот как это решается по-настоящему» работает лучше, чем вид, будто проблемы
не существует.

- Отдельно: показать **2D-сечение** — поле температур на плоскости среза как плоская картинка
  рядом. Вот здесь твой 2D-опыт работает напрямую, и для сварки поперечное сечение шва — один
  из главных видов.

## Шаг 9. Зонд и время — термический цикл

Два элемента, которые превращают демо из вьюера в инструмент.

### Шкала времени

- Ползунок шагов, кнопки play/pause, отображение номера шага.
- На смене шага: обновить атрибут `aScalar`, `needsUpdate = true`, `requestRender()`.
- При проигрывании рендер идёт непрерывно — это нормально, флаг рендера по требованию должен
  это учитывать.

### Зонд

- Клик по модели (шаг 6) ставит зонд: маркер в точке плюс запись индекса ближайшей вершины.
- Для этой вершины собрать значения по **всем шагам времени** — получается кривая.
- Нарисовать её на `#chart` обычным 2D-канвасом: оси, подписи, кривая, вертикальная линия
  текущего шага, горизонтальные линии порогов (плавление, фазовые превращения).
- **Связь в обе стороны:** клик по графику переводит сцену на этот шаг; смена шага двигает
  линию на графике. Связанные представления — то, чего ждут от инженерного инструмента.

Несколько зондов одновременно с разными цветами — ещё лучше, сразу видно разницу циклов в
разных точках шва.

### Что уметь объяснить

- Почему симуляцию нельзя показать одной картинкой и какие три представления нужны инженеру
- Что такое термический цикл и почему именно он важен для сварки
- Стратегии хранения данных по времени: всё в памяти против потоковой подгрузки

## Шаг 10. Панель счётчиков и честная производительность

Выводи в `#stats` и обновляй после каждого кадра:

```ts
const info = renderer.info;
info.render.calls        // вызовы отрисовки
info.render.triangles    // треугольники за кадр
info.memory.geometries   // число геометрий в памяти GPU
info.memory.textures     // число текстур
```

Плюс: время последнего кадра в миллисекундах, флаг «рендер в покое выключен», число вершин
модели.

### Специально проверь утечку

Загрузи модель десять раз подряд **без** `dispose()` старой геометрии и материала — и смотри,
как `memory.geometries` растёт. Потом добавь `dispose()` и убедись, что число стабильно.

**Это надо увидеть своими глазами.** Сборщик мусора JavaScript не освобождает буферы GPU, и
это самая частая утечка во вьюерах. На собесе рассказ «я специально воспроизвёл утечку и
смотрел на счётчик геометрий» звучит совершенно иначе, чем «надо вызывать dispose».

## Шаг 11. Необязательное, если останется время

По убыванию полезности для разговора:

1. **`three-mesh-bvh`** — поставить, подключить к мешу, замерить время picking до и после на
   тяжёлом меше (возьми модель на несколько сотен тысяч треугольников или размножь пластину).
   Таблица «треугольников / без BVH, мс / с BVH, мс» — это артефакт, на который можно ссылаться.
2. **GPU-пикинг по цвету** — отдельная сцена с материалами уникальных цветов, рендер в
   `WebGLRenderTarget`, `renderer.readRenderTargetPixels` для одного пикселя. Сравнить с лучом
   по времени отклика и по удобству выбора тонких элементов.
3. **`InstancedMesh`** — маркеры узлов сетки: сначала отдельными мешами (и увидеть, как падают
   кадры и растут вызовы отрисовки), потом одним InstancedMesh. Замер «вызовы отрисовки до/после».
4. **Marching cubes** — изоповерхность на объёмной решётке. Самое трудоёмкое, бери последним.

## Чем заканчиваем: что говорить на собесе

Не «я изучил Three.js за неделю». А так:

> Я собрал небольшой вьюер, чтобы проверить решения, которые считаю правильными для вашей
> задачи. Ортографическая камера по умолчанию, потому что по инженерной модели мерят.
> Поле подаётся атрибутом, а цвет берётся выборкой из одномерной текстуры палитры — тогда
> смена палитры и диапазона не требует перезагрузки геометрии на GPU, а это понадобится, как
> только появится интерактивная легенда и анимация по времени. Пороги в легенде привязаны к
> температуре плавления и фазовым превращениям, а не растянуты на min–max, потому что иначе
> цвет означает разное на разных шагах и расчёты нельзя сравнивать. Освещение почти убрано
> осознанно: оно искажает считывание цвета. Рендер по требованию, и вот счётчики вызовов
> отрисовки. Чего в нём нет — заглушки на срезе, она требует трафаретного прохода, и я
> понимаю, как это делается. И BVH я подключил только чтобы померить разницу, вот числа.

После такого разговор уходит с темы «умеет или нет» на тему архитектуры решений. Это та
территория, где опыт работает на тебя.
